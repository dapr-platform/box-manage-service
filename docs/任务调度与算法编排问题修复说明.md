## 二、详细说明

### 3. 自动调度任务停止后失败、无法重启

**根因（三处缺陷叠加）**
1. 监控轮询 `pollAllTaskStatus` 会取出**所有**带 `BoxID` 的任务。用户停止任务后盒子端任务已被删除，`GetTaskStatus` 返回 404/not found，`shouldMarkTaskFailed` 命中该分支 → 平台把任务 `Fail()` 成 `failed`。这是"一停止就显示失败"的直接来源。
2. `RetryTask` 只把 `status` 改回 `pending` 并清空 `LastError`，**不复位 `schedule_status`**（仍为 `assigned`），自动调度捞取条件要求 `schedule_status = unassigned` → 任务永远回不到调度池；同时监控又拿旧 `BoxID` 查到已删除的盒子任务 → 再次失败。
3. `UpdateTask` 保存时同样不复位绑定关系。

**改动**
- `service/box_monitoring.go`：仅当任务本地仍处于 `running` / `paused` / `run_status=running` 时，"盒子查不到任务"才标记失败；用户已停止的任务不再误标。
- `api/controllers/task_controller.go`：
  - `RetryTask`：`AutoSchedule` 任务重试后调用 `UnassignFromBox()`（清 BoxID、`schedule_status=unassigned`、`status=pending`）。
  - `UpdateTask`：保存时若任务启用自动调度、处于非运行态且仍残留盒子绑定 → `UnassignFromBox()`。

**失败判定标准（供排查参考）**
`status == failed` **或** `LastError` 非空 **或** 绑定盒子离线 → 视为失败态。

**上线注意**：修复后"停止"任务保持 `completed/stopped`，不再变为 `failed`；若业务上暂停语义为"完全停"，需复核 `paused` 的处理。

### 4. 任务详情视频帧全为蓝绿图

**排查结论**
- 手动截图（`handleRtspSnapshot`）的 OpenCV 分支对 3/1/4 通道均正确转 BGR，颜色无误。
- ffmpeg 回退分支命令中强制 `-vf "format=yuvj420p" -pix_fmt yuvj420p`，对 limited-range / 10bit 等源流会造成整片偏色。
- SSE 推送链路的颜色转换（`frame_data.cpp`）经核对正确，排除该成因。

**改动**：新增配置项 `stream_quality.snapshot_force_yuvj420p`（默认 `true` 保持历史行为）。
- `true`：命令含 `-vf "format=yuvj420p" -pix_fmt yuvj420p`（原行为）
- `false`：不加该转换，由 ffmpeg 按源流自然输出

**现场验证方法**：将 `config/config.yaml` 中该项设为 `false`，重启后重新截图；若蓝绿消失即为根因。

### 7. 模型芯片与盒子严格匹配（不匹配直接拒绝）

**根因**
1. 盒子端 `getSupportedHardware()` 仅解析 `/proc/cpuinfo` 的 `model name`，识别失败时**默认上报 `bm1684` + `bm1684x` 双平台** → 平台认为该 bm1684x 盒子"支持 bm1684"。
2. 平台 `boxSupportsChip()` 对**未声明硬件**的盒子直接放行。
3. 部署侧 `isHardwareCompatible()` 存在 `bm1684x 兼容 bm1684`、`bm1688 兼容 bm1684` 的降级规则。
4. 模型 key 解析只按固定分段取段，格式不符时解析为空 → 被视为"无芯片需求"而任意匹配。

**改动（盒子端）**
- `src/httplib_server.cpp`：`getSupportedHardware()` 改为**多来源探测**（`/proc/cpuinfo`、`/proc/device-tree/model`、`/sys/firmware/devicetree/base/model`、`/proc/version`），统一小写匹配，命中即上报**单一平台**；仅完全探测不到时保留历史默认并打印告警。

**改动（平台侧）**
- `service/task_scheduler_service.go`：
  - `extractChipFromModelKey()`：新增已知芯片白名单校验 + 全文 token 回退扫描（含 `bm1684x` 优先于 `bm1684`）。
  - `boxSupportsChip()`：改为**严格精确匹配**；盒子未声明硬件或声明中不含所需芯片 → 不兼容（不再放行），并打印原因。
  - 调度无候选盒子时返回明确拒绝：`没有找到兼容的盒子：任务需要芯片 bm1684x，但无盒子声明支持该芯片（已拒绝下发）`。
- `service/task_deployment_service.go`：
  - `isHardwareCompatible()`：移除跨芯片兼容规则，改为必须完全一致。
  - `DeployTaskWithLogging()` 新增 `Step 3.5/7` 芯片前置校验，调用新方法 `validateTaskChipCompatibility()`；不匹配直接返回 `ErrorCode = CHIP_NOT_COMPATIBLE`。

**覆盖性核查**：全部下发入口（手动部署、自动调度、故障迁移、故障转移、执行器、启动恢复）均汇聚到 `DeployTask` → `DeployTaskWithLogging`，校验无绕过路径；调度侧另有独立过滤，形成双重保障。

**⚠️ 上线前必做**：确认所有盒子 `/api/v1/meta` 能正确上报单个芯片平台，否则未声明/错报硬件的盒子将被拒绝接收带芯片需求的任务。
```bash
curl -k https://<盒子IP>:9000/api/v1/meta | grep -A3 supported_hardware
# 期望：["bm1684x"] 等单平台，且日志出现 "Detected supported hardware: bm1684x"
```

### 8. 算法编排工作实例存储量估算口径

- `348KB` 是**单个工作流实例**的全量 JSON（图片走图片缓存外置引用，非内联 base64，故不是稳定均值）。
- 正确估算式：**总占用 ≈ 单实例体积 × 每日触发实例数 × 保留天数**（注意不是乘视频帧数）。
- 系统已有自动清理：`data_retention` 默认 `log_retention_days=15`、`instance_retention_days=15`、每 24h 常规清理；磁盘水位 ≥ 85% 触发紧急清理（日志保留 0 天、实例保留 7 天）并执行 `WAL checkpoint + VACUUM`。**15 天是滚动上限，不是无界累积**。
- 满帧（每帧触发）会推算到 TB 级 → 说明触发必须限流（见第 9 项）。

### 9. 推理任务负载过大自停且无提醒

**根因**：任务转发循环中每批结果都会调用 `WorkflowExecutor::createAndRunInstance()`，该函数**每次新建线程执行且无任何并发上限 / 队列 / 节流**。满帧绑定工作流时，实例与线程数量线性膨胀，耗尽盒子资源导致任务失去响应。此外工作流实例是推理任务"触发"产生的，二者非父子关系，停实例不会停止持续触发的推理任务。

**改动（box-app）**
- 新增配置（`config/config.yaml` 的 `workflow` 段）：
  - `trigger_min_interval_ms: 1000` — 同一推理任务两次触发工作流的最小间隔，`<=0` 不限制
  - `max_concurrent_instances: 8` — 单个部署同时运行的最大工作流实例数，超出丢弃触发，`<=0` 不限制
  - `throttle_log_enabled: true` — 被节流时输出告警日志
- `src/task_manager.cpp`：在触发分支前按 `task_idx` 做限频，超限跳过并记录 `[FWD-WF][THROTTLE]` 告警。
- `src/workflow_executor.cpp`：`createAndRunInstance()` 入口做并发上限只读检查，超限丢弃并记录 `[WorkflowExecutor][THROTTLE]` 告警；线程启动**之前**占用名额，线程结束/异常时释放（防止计数泄漏）。
- 相关头文件与配置解析/持久化同步更新。

**观察方式**：日志中出现 `THROTTLE` 关键字即表示触发达到了节流阈值，可据此调整上述阈值。
