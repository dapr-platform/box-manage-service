## 二、逐项分析

### 问题 1：列表接口体积爆炸（8.6MB / 16 秒）

**现象**：AI 快速编排弹窗的模板下拉框显示「暂无数据」，但接口返回 200。

**实测数据**：

```
GET /api/v1/workflows/all?page=1&page_size=100
→ HTTP 200，耗时 16.4 秒，下载 9,043,439 字节（8.6MB）
→ 单条平均 83.9KB，其中 structure_json 平均 49.1KB，最大 132.9KB
```

**根因**：列表接口把每条编排的完整图 JSON 都返回了。模板下拉框只需要 id/名称/版本。

**为什么以前没暴露**：编排数据量涨到 256 条后，响应从 KB 级变成 MB 级。测试数据少时完全看不出来。

**修复**：
- `models.Workflow` 的 `structure_json` / `structure_json_view` 加 `omitempty`
- 新增 `Workflow.StripGraphPayload()`，在 4 个列表方法（`List` / `ListAll` / `ListAllWithFilters` / `Search`）返回前清空这两个字段
- 详情接口（`GetByID`）不清空，编辑器照常拿到完整图

**为什么不破坏编辑器**：先确认了全前端只有两处消费 `structure_json`，且都走 `fetchWorkflowDetail`（详情接口），不复用列表数据。

**修复后实测**（同参数对比，避免口径不一致）：

```
GET /api/v1/workflows/all?page=1&page_size=100
修复前：9,043,439 字节 / 16.4 秒 / 单条平均 83.9KB
修复后：   25,633 字节 / 0.48 秒 / 单条平均 0.26KB
→ 体积降到 1/353，耗时降到 1/34
```

按前端实际使用的 `page_size=500` 拉全量 263 条：66,572 字节 / 0.53 秒。

**遗留项**：列表里同一编排的多个版本会重复出现（如「人员入侵累计检测编排-2669」出现 16 次）。是否只显示每个 `key_name` 的最新版，属于产品决策，**未处理**。

### 问题 2：模型输出被截断，修复轮次永远无法收敛

**现象**：一次生成跑满 4 轮，错误数从 9 → 1 → 1 → 1 始终不动，最后被「连续无进展」保护拦下。

**实测特征**（10-17 某次生成的四轮响应体积）：

| 轮次 | 响应体积 | 耗时 |
|---|---|---|
| 第 1 轮 | 41,258 B | 56.6s |
| 第 2 轮 | 21,870 B | 51.3s |
| 第 3 轮 | 23,084 B | 52.0s |
| 第 4 轮 | 17,470 B | 43.7s |

第 1 轮完整（41KB），之后骤降到 17~23KB —— 这是截断的典型特征。

**根因**：请求体只有 `model` / `temperature` / `messages` / `top_k` / `enable_thinking`，**从未传 `max_tokens`**，服务端用默认上限（通常 4K~8K token）。一张 10 节点编排序列化约 15KB（≈6~8K token），必然被截断。

截断后 JSON 括号不闭合 → `extractJSONObject` 配对失败 → 返回空 → 上层报「不是合法 JSON」→ 拼接残的 `raw` 进入下一轮修复 → 模型拿到坏输入 → 永远修不好。

**修复**：
1. 新增配置 `LLM_MAX_OUTPUT_TOKENS`（默认 16384），请求显式带 `max_tokens`
2. 解析响应时读取 `finish_reason`，为 `length` 时直接返回明确错误（原来完全没读这个字段）
3. 前端检测到 `invalid_json` 时**立即暂停**，不再拿残缺 `raw` 空转（原来会白烧 3 轮 token）

**修复后实测**（10-17 17:43）：

```
第 1 轮  200  59,090B  2m30.4s   ← 完整
第 2 轮  200  38,688B  1m23.1s
→ 2 轮收敛成功
```

### 问题 3：校验器大面积误报（最耗时的一项）

**现象**：AI 生成后报 9 个错误，其中 6 个是假的。

**三个误报根因**（全部对照 box-app 源码确认）：

**① 裸 `ref_key_name` 是合法的上下文变量引用**

box-app 的 `resolveReference` 遇到无点号的引用会**先按变量名查上下文**：

```cpp
if (dot_pos == npos) { auto vit = variables_.find(ref); if (vit != end) return ...; }
```

所以开始节点写 `ref_key_name: "detections"`、`task_get_context` 写 `"is_alarmed"`，都是标准用法。校验器却要求所有引用必须是 `<节点id>.<输出key>` 格式。

**② `outputs` 上的 `ref_key_name` 不参与解析**

box-app 只把 `node["inputs"]` 交给 `resolveInputs`，输出是按变量名捕获的。校验器却把 inputs 和 outputs 一起校验了。

**③ `script_content` 不参与插值**

校验器扫描了**所有** config 值找 `{xxx}`。但设计文档明确写着「node.config 其他字段不插值」。结果模型脚本里的 Python f-string `f"已达{count}帧"` 被当成了编排引用。

**修复**：
- 无点号的引用直接放行（上下文变量）
- `ref_key_name` 只校验 inputs
- 新增 `interpolationInputKeys()`，严格按 box-app 的 6 个真实插值调用点界定范围（`mqtt.payload`、`http_request.{url,headers,body}`、`wechat_work.body`、`rpa_wechat_proxy.body_text`）

**同时还修了另一个过严规则**：`python_script` 的端口是用户自由定义的（前端有「+ 添加入参」按钮），但校验器要求必须命中模板的 `input`/`output`。已加入 `userDefinedPortTypes` 白名单，改为只检查 key_name 重复。

**教训**：校验器的每一条规则都必须对照**运行时源码**，而不是设计文档或直觉。误报的危害比漏报更大——它会淹没有效信息，让修复轮次无法收敛。

### 问题 4：超时被环境变量覆盖

**现象**：AI 生成稳定 503。

**实测**：

```
2026/10/16 15:40:12  ai-generate  503  in 1m0.02s   ← 精确 60 秒
```

**根因**：`.env` 里显式写了 `LLM_REQUEST_TIMEOUT=60s`。环境变量优先级高于代码默认值，所以我改了代码默认值（60s → 180s）**完全没有生效**。

**排查方法**：进入容器看环境变量

```bash
docker exec <container> env | grep LLM_
```

**修复**：
- 线上 `.env` 改为 `LLM_REQUEST_TIMEOUT=300s`
- 后来实测发现 180s 仍不够（第 1 轮耗时 2m30s），已确认调至 300s 生效

**关键教训**：**改代码默认值之前，先确认线上有没有显式配置覆盖它**。这一条让我们多花了一轮发版。

---

### 问题 5：失败时丢弃已有成果

**现象**：前几轮已经生成出可用编排，但第 3 轮网络超时后，界面只剩「重试」，点了就把成果清空。

**根因**：`catch` 里无条件 `phase = 'failed'`，而 `failed` 态的主按钮是「重试」，走的是 `start()` → `reset()`。

**修复**：
- 已有可用结果时改为 `paused`，提供「继续修复 / 补充说明后重新生成 / 导入当前结果」
- 兜底：即使是 `failed` 态，只要还有结果，主按钮也是「导入画布」
- 只有第一轮就失败（确实什么都没有）才保持 `failed`

---

### 问题 6：下拉框首次打开为空

**现象**：第一次点开 AI 编排弹窗，模板下拉没有数据；关掉再点一次就正常。

**根因**：用 `<a-select-option>` 插槽形式时，首次渲染阶段 `children` 是 VNode/函数。antd 做搜索过滤时 `String(children)` 得到 `"[object Object]"`，空搜索词也会把选项滤掉。第二次打开时组件已渲染过，`children` 是纯文本，所以正常。

**修复**：
- 改用 `options` 数组，显式提供纯字符串 `label` 和 `searchText`
- 过滤函数保证**空搜索词返回 true**
- 顺带修了并发隐患：`loadTemplates` 原来并发调用时第二个直接返回空，改为返回同一个 in-flight promise

### 问题 7~9：模型行为问题

这三个是「编排能生成，但语义不对」，校验器看不出来，只能靠提示词约束与新增规则。

**问题 7：自行发明需求**

需求只说「停留超过 30 帧报警」，模型加了 `ENTER_THRESHOLD = 4` 的进入态，把实际报警推迟到第 34 帧（判断写成 `count > 4 + 30 - 1`）。

修复：提示词新增第 0 条「忠于需求（最高优先级）」，明确禁止增加需求没提到的阈值/状态/冷却期，并写明「超过 30 帧」= 第 31 帧（`> 30`，不是 `>= 30`）。

**问题 8：枚举参数被猜测**

模型给 `detection_filter.class_id` 填了 `2`。参考模板里该字段是 `null`（不按类别过滤）。**如果猜错，编排能正常跑但永远不触发，而校验器完全看不出来**——这是最危险的一类错误。

修复：提示词规定枚举/类别类参数**默认必须留空**，需求里没说就必须反问，不许猜。反问示例里的 `"default": "2"` 也一并改成了「留空（所有类别）」。

**问题 9：声明了却不使用的输出**

模型声明了 `need_notify` 并在脚本里置位，但它不参与任何连线，导致「恢复通知」（含最关键的**警报解除通知**）永远发不出去。

修复：新增校验规则 `unused_output`（警告级），检测「声明但既没被引用、也没参与分支条件」的输出。

**该规则的两次自我修正**：
1. 初版把 `detection_filter` 的 `matched_detections` 也报了 —— 固定契约节点的内置输出本来就常常用不到，规则收窄为只检查用户自由声明端口的节点
2. 线上又报出 `task_get_context.context` 和 `task_set_context.saved` —— 这两个是模板内置输出，新增 `templateOutputKeys()` 跳过模板已定义的 key

同时补了反向测试 `TestUnusedOutputStillCatchesCustomOnContextNode`，确保模型在上下文节点上自己声明的输出**仍然会被报出**，豁免没有放开过头。

### 问题 10：反问无法自定义回答

**现象**：反问界面只有「按默认处理」，用户没法给出真实答案。

**三个具体缺陷**：
1. **没有选项的问题**（如「SMTP 服务器地址是多少」）完全不显示输入框 —— 这是最常见的情况
2. **多选题**只有一个「补充说明」框，且勾不勾选都算进答案
3. 空着「自定义」也能提交

**修复**：
- 无选项的问题强制显示输入框
- 多选题新增「自定义」勾选框，**勾了才计入**
- 空着会飘红提示并阻止提交
- 底部新增「提交回答并继续生成」按钮

**测试抓到的真实 bug**：把答案逻辑抽成纯函数后立刻报错——**没有选项的问题，用户填了内容也不会提交**（`collectAnswers` 只在 `answers[index] === '__custom__'` 时才读输入框）。这段逻辑藏在模板和响应式状态里时，读代码看不出问题。

---

### 问题 11：无法对话式修改

**现象**：生成完成后只能关掉重新来，不能「让它把脚本补上」或「告警改成每 2 分钟」。

**修复**：
- 后端 `previous` 结构新增 `feedback` 字段，提示词中以「【用户对编排的修改要求（优先级高于自动修复，必须落实）】」呈现
- 前端新增对话输入框与对话历史，只要已有编排就可随时提要求
- `sendFeedback()` 保留上一轮 `raw` 与校验错误，只叠加用户意见，因此在原编排上迭代而非重来

---

### 问题 12：空脚本节点能通过校验

**现象**：界面显示「校验通过」，可导入的编排里 Python 节点却没有脚本 —— 运行时必然失败。

**根因**：`python_script_empty` 和 `python_script_invalid` 被放进 `Warnings`，不阻断 `valid`。

**修复**：这两类升级为 `error`；`validatePythonOutputs` 的其他问题（如输出未赋值）仍为警告。

## 四、排查手册

遇到「AI 编排不好使」时，按此顺序排查：

### 1. 先确认线上到底是什么版本

```bash
# 容器内二进制时间
docker exec local_box_center-box-manage-service-1 ls -l /app/box-manage-service

# 镜像构建时间
docker inspect -f '{{.Created}}' registry.cn-hangzhou.aliyuncs.com/daprplatform/box-manage-service:latest
```

本次排查中多次出现「代码已改但线上是旧镜像」，导致误判。

### 2. 看环境变量有没有覆盖代码默认值

```bash
docker exec local_box_center-box-manage-service-1 env | grep LLM_
```

### 3. 看 LLM 调用耗时

```bash
docker logs --since 30m local_box_center-box-manage-service-1 2>&1 | grep '\[LLM\]'
```

输出示例：

```
[LLM] 调用完成，耗时 15.364s（预算 5m0s）
```

用掉预算 80% 以上会变成警告，并提示调大超时或关闭 thinking。

### 4. 看 AI 生成的请求/响应体积

```bash
docker logs --since 30m local_box_center-box-manage-service-1 2>&1 | grep 'ai-generate'
```

正常应在 35~60KB。**若某轮骤降到 20KB 以下，基本就是被截断了。**

### 5. 量列表接口

```bash
curl -s -m 60 -o /tmp/all.json -w "HTTP %{http_code} 耗时 %{time_total}s 体积 %{size_download}B\n" \
  "http://<host>/api/box-manage-service/api/v1/workflows/all?page=1&page_size=100"
```

正常应在 100KB 以内。若接近 MB 级，说明 `structure_json` 又被返回了。

## 五、经验教训

### 1. 校验规则必须对照运行时源码，不能凭设计文档或直觉

本次 6 个误报全部源于「想当然」。校验器的任务是**发现真问题**，不是**证明自己很严格**。误报的危害远大于漏报：它淹没有效信息，让自动修复循环永远无法收敛。

### 2. 改默认值前先确认真实配置来源

代码里把 60s 改成 180s，但 `.env` 写死 60s，改了个寂寞。多花了一轮发版。

### 3. 「代码已修改」≠「问题已修复」

排查过程中多次因为线上跑旧镜像而误判。**任何一次验证前，先确认版本**。

### 4. 阶段性测试数据量不足，会掩盖性能问题

8.6MB 的接口在 10 条数据时完全正常。本次是数据涨到 256 条才暴露。

### 5. 纯函数 + 单测能发现读代码发现不了的 bug

答案收集逻辑抽出来之后立刻暴露「无选项时用户输入被丢弃」。藏在模板字符串和响应式状态里的逻辑，靠 review 很难发现。

### 6. 对模型的约束要写成可检查的规则

「不许自行发明需求」只写进提示词是不够的，还要有 `unused_output` 这样的**机器可检查规则**兜底。提示词管生成，校验器管验收，两者缺一不可。

### 7. 失败路径要保留用户成果

任何中间轮次产出的结果都是用户等待的成本。失败态不应等于「清空重来」。
