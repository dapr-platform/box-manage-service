## 二、接口一：任务视频帧截图

### 2.1 接口定义

```http
POST /api/v1/tasks/{id}/snapshot
```

- 路由已注册（`api/routes.go`），Swagger 已更新（`/api/v1/tasks/{id}/snapshot`）
- 平台内部会代理到盒子的 `POST /api/v1/rtsp/snapshot`
- `{id}` 传**平台任务 ID**（数据库主键，即列表页 `record.id`）

### 2.2 请求

无请求体。建议超时给足（**建议 ≥ 60s**）——接口内部要拉 RTSP 流，实测较慢。

```ts
// baseUrl 约定参考 services/video.ts 的 downloadVideoFile 写法
const base = boxManageApi.baseUrl; // "/box-manage-service"
const url = `/api${base}/api/v1/tasks/${taskId}/snapshot`;

const resp = await fetch(url, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${localStorage.getItem("token") || ""}`,
  },
});
```

### 2.3 成功响应（HTTP 200）

平台按**统一响应格式**包装后返回，`data` 内是盒子的原始响应：

```json
{
  "code": 0,
  "message": "截图成功",
  "data": {
    "success": true,
    "image_data": "data:image/jpeg;base64,/9j/4AAQSkZJRg...",
    "image_width": 1920,
    "image_height": 1080,
    "capture_method": "opencv",
    "timestamp": "2026-09-17 15:47:53"
  },
  "timestamp": "2026-09-17 18:00:00"
}
```

**`data` 内关键字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `image_data` | string | **完整 data URL**，可直接塞进 `<img :src>`，**无需再拼前缀** |
| `image_width` / `image_height` | number | 图像尺寸，可用于等比布局 |
| `capture_method` | string | `opencv` / `ffmpeg`（仅调试参考） |

> ✅ **重点**：字段名是 **`image_data`**，且值**已经是** `data:image/jpeg;base64,xxx` 形式。
> 前端**不要**再写 `"data:image/jpeg;base64," + image_data`，否则会得到 `data:image/jpeg;base64,data:image/jpeg;base64,...` 导致图片不显示。

### 2.4 失败响应

平台在以下情况返回非 200，**统一为平台格式**（与成功响应同构，便于统一解析）：

```json
{ "code": 400, "message": "任务未部署到盒子，无法截图", "data": null, "timestamp": "..." }
```

| 场景 | HTTP | message |
|---|---|---|
| 任务不存在 | 404 | 任务不存在 |
| 任务未分配盒子 | 400 | 任务未部署到盒子，无法截图 |
| 任务未关联视频源 | 400 | 任务未关联视频源，无法截图 |
| 盒子截图失败 | 500 | 盒子截图失败(HTTP xxx) |
| 盒子返回 `success:false` | 500 | 盒子给出的 message（如"图像编码失败"） |
| 盒子响应非 JSON | 500 | 盒子截图响应格式错误 |
| 获取盒子信息失败 | 500 | 获取盒子信息失败 |

> 💡 若盒子自身返回 `success:false`，平台会**按其 message 转成失败响应**，不会把 `success:false` 藏在 200 里。**因此前端只需判断 HTTP 状态码即可**，不必再检查 `data.success`。

### 2.5 建议的前端实现

```ts
async function getTaskSnapshot(taskId: number | string): Promise<string> {
  const url = `/api${boxManageApi.baseUrl}/api/v1/tasks/${taskId}/snapshot`;
  const resp = await fetch(url, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${localStorage.getItem("token") || ""}`,
    },
  });

  const body = await resp.json().catch(() => ({}));

  // 失败统一走这里（平台已把盒子 success:false 也转成失败响应）
  if (!resp.ok) {
    throw new Error(body?.message || `截图失败: ${resp.status}`);
  }

  const imageData = body?.data?.image_data;
  if (!imageData) {
    throw new Error(body?.message || "截图接口未返回图片数据");
  }
  // image_data 已是完整 data URL，直接返回，不要拼前缀
  return imageData;
}
```

`captureFrame()` 改为：

```ts
const captureFrame = async () => {
  capturing.value = true;
  try {
    capturedFrame.value = await getTaskSnapshot(taskId.value);
    message.success("视频帧截取成功");
  } catch (e: any) {
    message.error(e.message || "截图失败");
  } finally {
    capturing.value = false;
  }
};
```

### 2.6 注意事项

1. **去掉 `onMounted` 里的自动调用**：现有代码在任务 `running` 时进页面 1 秒后自动截图，且每 5 秒轮询有 20% 概率重截。真实截图较慢（要拉流），建议改为**用户点击按钮才截**。
2. **必须有 `box_id`**：任务未分配盒子时接口直接返回 400，前端可据此禁用按钮。
3. **必须有视频源**：任务未关联 `video_source` 时返回 400。

## 三、接口二：推理结果图流（SSE）

### 3.1 接口定义

```http
GET /api/v1/tasks/{id}/sse
Content-Type: text/event-stream
```

- 路由已存在（`api/routes.go:494`，`taskController.GetTaskSSEStream`）
- 平台代理到盒子的 `GET /api/v1/sse/{taskId}`
- 长连接，无超时

### 3.2 ⚠️ 前提：前端页面尚不存在（**必须新建**）

当前 `src/router/index.ts` 中**没有任何 `sse` 路由**，`src/pages/task/` 下也无对应组件。

而 `TaskDetail.vue` 里已有跳转：

```ts
window.open(`/tasks/sse/${taskId}`, "_blank");   // TaskDetail.vue:826
```

**这个跳转会打开空白页。** 需新建一个 SSE 图流页面并注册路由（如 `/tasks/sse/:id`）。

### 3.3 图流开关判断

任务详情返回的 `inference_tasks[].sendSSEImage` 决定是否推送。现有代码已正确判断：

```ts
const hasSSEStream = computed(() =>
  taskDetail.value?.inference_tasks?.some((t) => t.sendSSEImage) || false
);
```

> 后端已修复：平台下发时会将该字段兜底为 `true`（详见第四节），因此**新建的任务应默认能看到图流**。

### 3.4 SSE 消息格式（已核对盒子源码）

消息由盒子 `src/sse_manager.cpp:176` 构造，**每个事件的 `data` 是一个 JSON**：

```
data: {"type":"image","taskId":"task_xxx","image":"data:image/jpeg;base64,/9j/4AAQ...","metadata":{...}}

```

即完整形状：

```json
{
  "type": "image",
  "taskId": "task_1781082839088_n4e3y11yl",
  "image": "data:image/jpeg;base64,/9j/4AAQSkZJRg...",
  "metadata": {
    "timestamp": 1789631088717,
    "has_drawn_results": true,
    "hardware_accelerated": false,
    "task_id": "task_1781082839088_n4e3y11yl",
    "model_name": "detection-yolov8-BM1684X-yolov8n_BM1684X_F16",
    "result_type": "detection",
    "frame_id": 12345,
    "success": true,
    "inference_results": [ /* 推理结果数组，仅在 success 且有结果时出现 */ ],
    "error_message": "..." 
  }
}
```

**字段说明**（来源 `unified_image_processor.cpp:461 createMetadata`）：

| 字段 | 说明 |
|---|---|
| `type` | 固定 `"image"`，可用于区分消息类型 |
| `image` | **完整 data URL**，直接塞 `<img :src>` 即可 |
| `metadata.timestamp` | 毫秒时间戳 |
| `metadata.has_drawn_results` | 是否已绘制检测框 |
| `metadata.model_name` | 模型 key |
| `metadata.frame_id` | 帧号 |
| `metadata.success` | 推理是否成功 |
| `metadata.inference_results` | 推理结果数组（条件性出现，需判空） |
| `metadata.error_message` | 失败原因（条件性出现） |

> ⚠️ `metadata` 为**可选字段**，且 `inference_results` / `error_message` 也是条件性出现，前端务必判空。

### 3.5 前端消费示例

#### ⚠️ 先注意两点（复用现有 `utils/sse.ts` 时会踩到）

1. **任务图流不应复用现有白名单**：`src/utils/sse.ts` 已有一个成熟的 `SSEClient`（带自动重连、token 注入），但它的 `SSEEventType` 是**工作流事件的白名单**：

   ```ts
   export type SSEEventType =
     | 'workflow.started' | 'workflow.paused' | ... | 'progress.updated'
   ```

   任务图流的 `type` 是 **`"image"`**，**不在该白名单内**，直接复用会 TS 类型报错。

2. **`handleMessage` 会 `console.log` 每条消息**：图流每秒可能多帧，复用会刷爆控制台，建议单独实现或先去掉该日志。

**建议**：为任务图流**单独写一个轻量连接**（不必改造 `SSEClient`），或把 `SSEEventType` 放宽为 `| 'image' | (string & {})`。

#### 推荐实现

```ts
const es = new EventSource(`/api${boxManageApi.baseUrl}/api/v1/tasks/${taskId}/sse`);

es.onmessage = (ev) => {
  const msg = JSON.parse(ev.data);
  if (msg.type !== "image" || !msg.image) return;

  // image 已是完整 data URL，直接赋值
  frameSrc.value = msg.image;

  const meta = msg.metadata;
  if (meta) {
    // 注意 inference_results / error_message 可能不存在
    boxes.value = meta.inference_results ?? [];
    if (meta.success === false && meta.error_message) {
      console.warn("推理失败:", meta.error_message);
    }
  }
};

es.onerror = (e) => {
  console.error("SSE 连接异常", e);
  // 按需重连
};
```

> 💡 若需 token 鉴权，参考 `utils/sse.ts` 中 `?token=${localStorage.getItem('token')}` 的写法拼接查询参数。

### 3.6 已知风险（需联调确认）

1. **同步任务可能 404**：平台拼 URL 用的是 `task.TaskID`，而同步任务的 `TaskID` 是 `sync_{boxID}_{externalID}`，盒子上的真实 ID 存在 `ExternalID`。**若同步任务打不开图流，请反馈，这属后端问题。**
2. **需任务处于运行态且已分配盒子**，否则盒子端无图可推。
3. 盒子需有订阅者才会广播，前端连接建立后应能看到推送。

## 四、后端已修复内容（供前端了解）

### 4.1 问题 5：下发链路 `sendSSEImage` 兜底

`service/task_deployment_service.go` 新增 `resolveSendSSEImage()`：平台下发任务时，若该字段未显式开启，按下发默认值 `true` 处理，使**下发任务与同步任务行为一致**。

同时 `models/deployment.go` 去掉了该字段的 `omitempty`，现在 `false` 也会显式出现在接口响应中（便于排查）。

**对前端的影响**：
- 任务详情接口现在能明确看到 `sendSSEImage` 的真值
- 新建任务若不传该字段，后端会兜底为 `true`

### 4.2 问题 10：执行设备筛选显示 ID

`repository/task_repository.go` 为 5 个筛选方法补了 `Preload("Box")`。**前端无需改动**，筛选后执行设备列会正常显示盒子名称。

### 4.3 附带修复：盒子上线恢复无限失败

`models/workflow_schedule.go` 的 `DeploymentIDs` 字段类型错误（`JSONMap` 存数组），导致平台恢复流程报错并**无限重试**（205 盒子上已复现 18357 次）。已改为新增的 `JSONArray` 类型。

**对前端的影响**：工作流调度相关的接口若返回 `deployment_ids`，现在是**数组**（如 `[]` 或 `[1,2]`），此前因扫描失败可能导致接口报错。若前端有引用该字段，请按数组处理。
