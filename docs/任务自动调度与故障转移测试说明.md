# 任务自动调度与故障转移测试说明

## 1. 测试目标

验证以下功能：

- 自动调度器能够发现待调度任务并选择合适的在线盒子。
- 盒子离线后，启用自动调度的任务能够迁移到其他在线盒子并重新部署。
- 盒端任务同步不会重复创建本地任务。
- 调度历史能够记录自动调度和故障转移结果。
- 系统配置中的自动调度开关和调度间隔能够即时生效。

## 2. 测试环境

准备至少两个盒子：

| 盒子 | 初始状态 | 用途 |
| --- | --- | --- |
| 206 | 在线 | 原任务运行盒子 |
| 207 | 在线 | 故障转移目标盒子 |

准备一个可以正常运行的任务配置，包括视频源、模型和推理配置。建议任务使用唯一的盒端任务 ID，避免与历史测试数据混淆。

测试前确认：

1. 管理服务、数据库和 Dapr 正常运行。
2. 206、207 的健康检查和心跳正常。
3. 206、207 的模型依赖满足。
4. 任务字段 `auto_schedule=true`。
5. 当前存在一个启用的调度策略。
6. 记录服务的 `BASE_CONTEXT`，以下接口路径需要拼接该前缀。

## 3. 常用接口

```text
GET  /api/v1/auto-scheduler/status
POST /api/v1/auto-scheduler/start
POST /api/v1/auto-scheduler/stop
POST /api/v1/auto-scheduler/trigger
POST /api/v1/scheduler/schedule/{taskId}
GET  /api/v1/scheduler/history
POST /api/v1/boxes/{boxId}/sync-tasks
```

## 4. 测试用例

### TC-01 自动调度器启动和停止

前置条件：系统配置中的 `task.auto_schedule_enabled=true`。

步骤：

1. 查询 `/api/v1/auto-scheduler/status`。
2. 确认 `is_running=true`。
3. 调用停止接口，再查询状态。
4. 调用启动接口，再查询状态。

预期：

- 启动后 `is_running=true`，停止后为 `false`。
- 状态中能看到调度间隔、在线盒子数和待调度任务数。

### TC-02 自动调度分配任务

前置条件：创建一个未分配任务，并设置：

```text
auto_schedule=true
schedule_status=unassigned
run_status=stopped
status=pending
```

步骤：

1. 确认 206、207 在线。
2. 调用 `/api/v1/auto-scheduler/trigger`，或等待定时周期。
3. 查询任务详情。

预期：

- 任务被分配到符合策略的盒子。
- `box_id` 被设置，`schedule_status=assigned`，兼容字段 `status=scheduled`。
- `/api/v1/scheduler/history` 能查到对应记录。
- 自动调度本身只负责分配，不保证任务已经下发到盒端；需要继续执行部署或任务执行流程。

### TC-03 任务在两个盒子之间实际部署

步骤：

1. 将任务部署到 206，确认 206 上能查询到该任务。
2. 调用任务执行或重新部署接口，指定 207 作为目标盒子。
3. 查询管理端任务和 207 的任务列表。

预期：

- 207 上存在同一个盒端任务 ID。
- 管理端 `box_id` 更新为 207。
- 任务配置、模型和视频源正确。
- 若任务设置 `auto_start=true`，盒端按配置自动启动；否则不应因为普通调度自动启动。

### TC-04 盒子离线故障转移

前置条件：

- 任务已经部署到 206。
- 任务 `auto_schedule=true`。
- 任务处于运行中，或调度策略配置 `execution_config.auto_start_task=true`。
- 207 在线且满足调度策略。

步骤：

1. 停止 206 的心跳或使 206 健康检查不可达。
2. 等待监控将 206 判定为离线（默认心跳超时约 5 分钟）。
3. 查看服务日志中的 `[TaskFailover]`。
4. 查询任务详情和 207 的任务列表。

预期：

- 206 状态变为 `offline`。
- 任务先解除 206 绑定，再选择在线候选盒子。
- 系统调用部署服务将任务实际下发到 207。
- 成功后任务 `box_id=207`、`schedule_status=assigned`、`LastError` 为空。
- 原任务处于运行状态或策略要求启动时，207 上任务被启动。
- `/api/v1/scheduler/history` 出现 `trigger=failover` 的记录。

### TC-05 故障转移无可用盒子

步骤：

1. 让 206 离线。
2. 同时让 207 离线，或将 207 资源/标签设置为不满足策略。
3. 等待故障转移执行。

预期：

- 日志出现“没有可用候选盒子”或候选部署失败。
- 任务保持 `box_id=null`、`schedule_status=unassigned`、`run_status=stopped`。
- `LastError` 记录失败原因。
- 任务不会被错误地标记为已部署到 207。

### TC-06 目标盒子任务数限制

步骤：

1. 将目标盒子的活跃任务数设置到策略上限。
2. 触发自动调度或故障转移。
3. 再停止其中一个活跃任务并重新触发。

预期：

- 达到上限时，该盒子不会进入候选结果。
- 停止任务不应被误计为运行中的活跃任务。
- 释放容量后，任务可以重新进入候选并部署。

### TC-07 盒端任务同步幂等性

步骤：

1. 在 206 上保留一个已存在任务。
2. 连续调用 `/api/v1/boxes/206/sync-tasks` 多次，或连续发送包含该任务的心跳。
3. 查询管理端任务列表。

预期：

- 同一个盒端任务只对应一条本地任务记录。
- 不应反复生成新的 `sync_*` 任务。
- 已有任务的状态、推理统计和 `ExternalID` 被更新。

### TC-08 任务执行失败与故障转移边界

步骤：

1. 让盒端任务返回 `failed/error`，或使任务状态接口返回 404。
2. 查询管理端任务状态。

预期：

- 管理端任务可能被标记为 `failed`，并记录 `LastError`。
- 当前实现不会因为单个任务推理失败自动迁移到其他盒子。
- 只有盒子离线/健康检查失败触发故障转移流程。

### TC-09 盒子重新上线触发调度

步骤：

1. 让一个盒子离线。
2. 确认其待迁移任务处于未分配状态。
3. 恢复盒子心跳。
4. 查询服务日志和自动调度器状态。

预期：

- 盒子恢复为在线后触发 `OnBoxOnline`。
- 若自动调度器运行且策略启用 `on_box_online`，会执行一次调度。
- 若策略未启用该触发条件，任务应等待定时调度或手动触发。

### TC-10 系统配置保存和生效

步骤：

1. 修改并保存 `task.auto_schedule_enabled`。
2. 查询自动调度器状态。
3. 修改并保存 `task.schedule_interval_seconds`。
4. 观察下一次调度周期。
5. 修改每盒最大任务数、默认优先级、重试次数和部署超时，并重新读取配置。

预期：

- 自动调度开关保存后立即启动或停止调度器。
- 调度间隔保存后被调度器采用；若策略配置了自己的间隔，以策略间隔为准。
- 其他配置可以保存和回读，但当前版本尚未接入对应业务逻辑，不应据此判断调度行为发生变化。

## 5. 日志和数据检查

重点关注以下日志关键字：

```text
[AutoSchedulerService]
[TaskFailover]
[BoxMonitoringService]
[BoxClientService]
```

重点检查字段：

```text
box_id
external_id
schedule_status
run_status
status
last_error
is_synchronized
```

## 6. 验收标准

- 盒子离线后，符合条件的任务能够实际出现在候选盒子上，而不是只更新管理端 `box_id`。
- 故障转移失败时任务不会显示为成功分配，并且有明确错误原因。
- 同一个盒端任务不会因心跳竞态产生重复本地任务。
- 自动调度和故障转移均能查询到调度历史。
- 单任务执行失败与盒子离线故障转移行为能够明确区分。

## 7. 已知限制

1. 普通自动调度只做盒子选择和本地分配，不自动调用部署服务。
2. 单个任务推理失败目前不会自动故障转移。
3. 默认离线判定等待时间约为 5 分钟，端到端测试需要预留等待时间。
4. `task.max_concurrent_per_box`、`task.retry_max_attempts` 和 `task.deployment_timeout_seconds` 当前只保存配置，尚未完全接入调度和部署逻辑。
