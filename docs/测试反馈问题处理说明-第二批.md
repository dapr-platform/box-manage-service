## 二、详细说明

### 2 & 3. 三个默认调度策略的真实行为

> ⚠️ **本篇修正了第一批文档中"策略为链式生效（按 priority DESC 逐条判断，首个匹配胜出）"的结论。该结论与代码不符。**

#### 2.1 并不存在"3 个自动生效的默认策略"

`models.DefaultSchedulePolicy()`（`models/schedule_policy.go:150`）只是一个**构造函数**，唯一调用点是手动接口：

```
POST /api/v1/schedule-policies/defaults?type=priority|load_balance|resource_match
```

- `migrations/` 下 6 个 SQL **均无** `INSERT INTO schedule_policies`；
- 启动初始化只执行 workflow / node_template / dictionary 三个 SQL；
- 反向证据：`scripts/reset_db.sh:48` 把 `schedule_policies` 列入 `TRUNCATE TABLE`。

**结论**：全新环境该表为空 → `GetDefaultPolicy()` 报错 → 自动调度降级到 `executeDefaultSchedule`（不限策略，走通用评分）。

#### 2.2 触发条件（真实逻辑）

| 触发方式 | 是否实现 | 说明 |
|---|---|---|
| 定时轮询 | ✅ | `time.Ticker`（`auto_scheduler_service.go:262-305`），**无 cron 解析** |
| 盒子上线 `on_box_online` | ✅ | `box_monitoring.go:497`、`box_client_service.go:281`，只取**第一条**满足的策略 |
| 新任务创建 `on_new_task` | ❌ | `OnNewTask()` **无任何生产端调用方**，死代码 |
| `on_task_failed` / `on_resource_change` | ❌ | 字段存在，无判定逻辑 |
| `cron_expression` | ❌ | 字段存在，从未解析 |

轮询间隔来自**当前那条策略**的 `trigger_conditions.interval_seconds`（默认 60s）；取不到则用系统配置 `task.schedule_interval_seconds`（默认 60s）。

待调度任务的捞取条件（`repository/task_repository.go:268-285`）：

```go
auto_schedule = true
AND schedule_status = 'unassigned'
AND run_status = 'stopped'
AND status NOT IN ('completed','cancelled','stopping')
ORDER BY priority DESC, created_at ASC LIMIT 50
```

#### 2.3 策略是"选一条执行"，不是链式

```go
policy, err := s.repoManager.SchedulePolicy().GetDefaultPolicy(ctx)   // 单条
if err != nil { return s.executeDefaultSchedule(ctx, startTime) }
return s.executeScheduleWithPolicy(ctx, policy)                        // switch 单一算法
```

`GetDefaultPolicy` = `WHERE is_enabled = true ORDER BY priority DESC LIMIT 1`（`repository/schedule_policy_repository.go:192-202`）。

> ⚠️ **三个默认策略的 `priority` 全是 `1`**（`models/schedule_policy.go:154`），而 `ORDER BY priority DESC` **没有第二排序键** → PostgreSQL 返回哪一行**不确定**。这就是"三个策略看不出区别"的真正原因：它们本来就只会随机生效一个，另外两个完全闲置。

#### 2.4 "启用回退策略"是什么？—— **未实现**

唯一相关字段 `ScheduleRules.EnableFallback`（`models/schedule_policy.go:128`，JSON `enable_fallback`）。

全仓库检索结果：**除定义处与默认值赋值外，零消费点**。

```
./models/schedule_policy.go:128  定义
./models/schedule_policy.go:198  默认值 true（负载均衡）
./models/schedule_policy.go:209  默认值 true（资源匹配）
```

**结论：勾选它不产生任何行为变化。** 唯一的"回退"是"表里一条启用策略都没有"时的 `executeDefaultSchedule` 降级，与该字段无关。

同样未被读取的字段：`PreferOnlineBoxes`、`PreferLessLoadedBox`、`SkipOfflineBoxes`、`MaxConcurrent`、`RetryAttempts`、`RetryIntervalSecs`、`TimeoutSeconds`、`ValidateBeforeRun`（仅 `AutoStartTask` 在故障转移路径被读，`box_monitoring.go:1261`）。

#### 2.5 资源匹配策略："标签严格匹配"究竟是什么

- 字段是 `require_tag_match`（默认 `false`），**不存在 `required_tags`**；比较的是 **`task.affinity_tags` vs `box.tags`**。
- 判定逻辑（`models/deployment.go:435-454`）：**交集非空即匹配（any-overlap）**，精确字符串 `==`（大小写敏感），**不是集合相等、不是子集**。
- 若 `task.affinity_tags` 为空 → **无条件兼容**。

⚠️ **实现不一致**：在通用评分路径中，**无论 `require_tag_match` 真假都会 `return nil` 剔除盒子**（`task_scheduler_service.go:432-439`），仅提示文案不同 —— 即 `false` 并未真正放宽过滤。

#### 2.6 最小匹配分数的**精确计算公式**

`calculateMatchScore()`（`service/auto_scheduler_service.go:639-678`），**满分 100**：

| 因子 | 计算式 | 最大贡献 |
|---|---|---|
| 基础分 | 常量 | **50.0** |
| 标签匹配 | `matchCount / len(affinityTags) * 30.0`；`affinityTags` 为空则固定 `+10.0`；不匹配且 `RequireTagMatch=false` 则 `+0` | **30.0** |
| 资源可用性 | `((100 - CPU%) + (100 - Mem%)) / 200 * 20.0` | **20.0** |
| 短路 | 盒子离线 → `return 0`；标签不匹配且 `RequireTagMatch=true` → `return 0` | — |

**注意**：`MinMatchScore`、CPU/Mem/TPU 阈值、盒子任务数、任务优先级、硬件、活跃任务数**都不参与这个分数**。

因此默认 `min_match_score = 60` 的实际含义是：**在线盒子基础就有 50 分**，只要资源不太满（资源分 >10 即 CPU+Mem 空闲度 >50%）或标签有一点匹配就能过线。所以"所有盒子都达不到分数"在实践中通常不会发生。

#### 2.7 单独开启各策略时的确切行为（测试问题 3 的直接答案）

**资源匹配策略单独开启：**

```go
score := s.calculateMatchScore(task, box, policy)
if policy.ScheduleRules.MinMatchScore > 0 && score < policy.ScheduleRules.MinMatchScore {
    continue                                    // ← 硬跳过，不参与竞争
}
if score > bestScore { bestScore = score; bestBox = box }   // ← 严格大于
```

- **都达不到分数线** → `bestBox == nil` → **不分配**，`SkippedTasks++`，原因 `"没有盒子满足资源匹配条件"`。**不会"矮子里拔将军"。**
- **多个盒子都过线** → **取最高分**；平局时取 `boxes` 中**第一个**（严格 `>` 判定）。
- **是否随机？→ 否。** 全仓库调度代码**无 `math/rand`**。平局的"先后"取决于 `FindOnlineBoxes`（无 `ORDER BY`）的数据库返回顺序。

**负载均衡策略单独开启：**

三条规则是**硬 AND 过滤**，任一不满足即 `continue`：
1. `currentLoad >= MaxTasksPerBox`（默认 5）
2. `!CanScheduleToBox(...)`（CPU ≥80% / Mem ≥80% / TPU ≥90% / 任务数超限，**达到即排除**）
3. `!task.IsCompatibleWithBox(box)`（标签）

- **全部不匹配或部分不匹配** → 逐条排除 → `bestBox == nil` → **不分配**，原因 `"没有可用的盒子满足负载均衡条件"`。**没有"选优"降级。**
- **全部匹配** → **取负载最低者**；平局取第一个。**不是随机。**
- 特点：它是**唯一带负载增量反馈**的策略（`boxTaskCount[bestBox.ID]++`），同一批 50 个任务会依次摊开。

**优先级策略单独开启：**

- **数字越大优先级越高**：`ORDER BY priority DESC`（策略选取）、`sortedTasks[j].Priority > sortedTasks[i].Priority`（任务排序，1-5）。
- **同优先级多盒子是随机分配吗？→ 否**，确定性（`sort.Slice` 降序 + 取 `[0]`）。

⚠️ **重要缺陷**：优先级加成只依赖**任务**优先级、**与盒子无关**：

```go
priorityScore := weights.PriorityWeight * policy.GetPriorityWeight(task.Priority) / 5.0
score.Score += priorityScore
```

对同一任务的所有候选盒子而言这是**常量偏移，不改变盒子间相对排序** —— 即"优先级策略"在**选盒**上毫无区分作用。它的真实效果仅来自**任务处理次序**（高优先级任务先抢占盒子）。

**多策略同时开启（真实默认状态）：** 因 `priority` 并列且无 tie-breaker，**只有一条会执行，且哪一条不确定**。

#### 2.8 另一个重大不一致（建议纳入整改）

**只有 `priority` 分支真正调用 `DeployTask` 把任务下发到盒子**；`load_balance` 与 `resource_match` **只写数据库字段（`status='scheduled'`、`schedule_status='assigned'`），不下发**（`auto_scheduler_service.go:523-524, 576-577`，代码注释亦自认此点）。

> 这可能与第 6 项"平台分配了但盒子上看不到任务"直接相关，建议现场比对：任务 `box_id` 已写入，但盒子任务列表无此任务。

### 4. 任务详情视频帧"全是蓝绿图"【已修复】

#### 根因：前端 Canvas 硬编码的假图

`front-hub-ng/apps/box-manage-web/src/pages/task/TaskDetail.vue` 的 `captureFrame()` 是一个 **TODO 桩函数**：

```ts
// TODO: 实现真实的视频截图API调用
// 这里模拟截图过程
await new Promise((resolve) => setTimeout(resolve, 1000));

// 模拟生成截图（实际应该调用后端API）
const canvas = document.createElement("canvas");
canvas.width = 640; canvas.height = 480;
const ctx = canvas.getContext("2d");
if (ctx) {
  // 生成模拟视频帧
  const gradient = ctx.createLinearGradient(0, 0, 640, 480);
  gradient.addColorStop(0, "#4CAF50");   // 绿
  gradient.addColorStop(1, "#2196F3");   // 蓝
  ctx.fillStyle = gradient;
  ctx.fillRect(0, 0, 640, 480);
  ...
  capturedFrame.value = canvas.toDataURL("image/jpeg", 0.8);

```

绿色 `#4CAF50` → 蓝色 `#2196F3` 的对角渐变，**正是现场看到的"蓝绿图"**。且 `onMounted` 会自动触发：任务 running 时进页面 1 秒后贴假图，此后每 5 秒轮询有 20% 概率重贴。

**这条链路完全不经过任何 HTTP 请求**，与盒子端颜色转换、编码、`yuvj420p` 全部无关。

#### 回答"配置开关是在盒子里吗？"

- `snapshot_force_yuvj420p` **存在且齐全**：`include/config_manager.hpp:141`、`config/config.yaml:77`、解析 `src/config_manager.cpp:377-378`。
- 它确实被传进 ffmpeg 命令（`src/httplib_server_tasks.cpp:1226-1230`），**但只作用于 `handleRtspSnapshot` 的 ffmpeg 回退分支**。
- 该接口在**平台侧从未被挂载为路由**（`box_proxy.go:862 GetRTSPSnapshot` 有定义、无路由），前端也从未调用 → **此前是一条死链路**。
- **对"任务详情蓝绿图"这一现象，调该开关无效。**

#### 改动

**前端** `TaskDetail.vue`：`captureFrame()` 改为调用真实接口 `taskService.getTaskSnapshot(taskId)`。

**前端** `services/task.ts`：新增 `getTaskSnapshot()`，POST `/api/box-manage-service/api/v1/tasks/{id}/snapshot`。

**平台** `api/routes.go` + `api/controllers/task_controller.go`：新增并实现 `POST /api/v1/tasks/{id}/snapshot`，代理到盒子 `POST /api/v1/rtsp/snapshot`，返回 base64 JPEG；已同步更新 swagger。

> 盒子上报的 `snapshot_force_yuvj420p` 开关仍然保留。接入真实截图后若发现颜色异常，再按第一批文档的方法把该项设为 `false` 复验。

### 5. 平台下发的任务看不到推理结果图流【已修复】

#### 根因：`sendSSEImage` 在下发链路上恒为 false

该字段是盒子端图片推送的**唯一门控**（`src/inference_task_base.cpp:840`）：

而两侧取值路径**不对称**：

**盒子端**（`src/task_config.cpp:368-372`）—— 缺字段即置 false 并持久化：

```cpp
if (task.contains("sendSSEImage"))
    taskConfig.sendSSEImage = task.at("sendSSEImage");
```


### 6. bm1684 模型被匹配到 bm1684x 盒子【已加固】

#### 先说结论：后端严格匹配代码是正确的

对四个关键函数逐一核对，**全部是精确相等比较，无一处用 `Contains` 做芯片兼容判断**：

| 函数 | 位置 | 比较方式 |
|---|---|---|
| `extractChipFromModelKey` | `task_scheduler_service.go:572` | `isKnownChip(parts[2])` 精确相等 |
| `boxSupportsChip` | `task_scheduler_service.go:626` | map 查表 `declared[chip]` |
| `isHardwareCompatible` | `task_deployment_service.go:907` | `target != required` |
| `validateTaskChipCompatibility` | `task_deployment_service.go:926` | `hw == chip` |

#### 那么 205 为什么还能接收 bm1684 任务？—— 两个数据面入口

**入口一：盒子端芯片探测失败，兜底上报双平台**

`src/httplib_server.cpp:765-826`：正常识别时**只上报单一平台**；**只有全部探测失败才上报 `["bm1684","bm1684x"]`**。此时严格匹配会被"合法"绕过。

**入口二：平台侧 `box.Meta` 陈旧**

`box.Meta` 的唯一写入点是 `box_monitoring.go:532`（Meta 轮询，默认 30s）；**心跳路径完全不碰 Meta**。若某次 `/api/v1/meta` 拉取失败，`metaInfo == nil` 会跳过赋值，随后 `baseRepository.Update` 用 `Save()` **整行覆写**，把内存中的**旧 Meta 原样写回**，而盒子仍被标记为 online。若该盒子历史上曾上报双平台，就会长期固化。

#### 改动（均为可观测性加固，不改判定逻辑）

1. `task_scheduler_service.go` / `task_deployment_service.go`：当盒子声明**多于一个**硬件平台时打印**醒目告警**，提示"疑似芯片探测失败或 Meta 陈旧，严格匹配可能失效"。
2. `src/httplib_server.cpp`：兜底分支补充醒目告警，并支持通过环境变量 `BOX_FALLBACK_HARDWARE=bm1684x` 指定单一平台上报（默认行为不变，保持对老设备兼容）。

### 8. 算法编排：每日触发次数与实例体积

#### 8.1 "把一个实例的所有日志下下来" ≠ 单实例体积

实例存储在盒子 `data/box.db`，无实例级 JSON blob：

- 主表 `workflow_instances`（`instance_id` 主键，含 `trigger_data`/`context_data`/`variables`）
- 子表 `node_instances`（含 `config`/`input_data`/`output_data`）、`variable_instances`、`line_instances`、`workflow_logs`，全部 `ON DELETE CASCADE`
- **图片不入库**：只把缓存 ID 写进结果（`task_result_aggregator.cpp:1010-1015`），图片本身在**内存 LRU**（`image_cache_manager.cpp:44`）

**下载日志与实例体积是"部分重叠"关系：**

| 计入日志 | 不计入日志 |
|---|---|

| | 图片缓存（纯内存，日志无法复现） |

**所以日志表往往是磁盘占用的主项，但不能代表实例全貌。**

### 12.（现场新发现）盒子上线恢复无限失败【已修复】

> 此项非测试反馈，是登录 205 排查时发现的**平台侧真实 bug**。

#### 现象

205 盒子日志中持续刷出，**已累计 18357 次**：

```
[StartupRecovery] 恢复失败，后续心跳将重试: session=restart-1789057022553-855060,
message=查询部署 91 的调度失败: sql: Scan error on column index 22,
name "deployment_ids": json: cannot unmarshal array into Go value of type models.JSONMap
[StartupRecovery] 恢复进行中: status=running, message=恢复任务已启动，第18357次尝试
```

每次心跳都重试、每次都失败 → **盒子上线后的部署恢复永远无法完成**。

#### 根因：字段类型与数据形态不匹配

`models/workflow_schedule.go:53`：

```go
DeploymentIDs JSONMap `gorm:"type:jsonb;not null;default:'[]'" json:"deployment_ids,omitempty"`
```

而 `JSONMap` 的定义（`models/workflow_instance.go:66`）是**对象**：

```go
type JSONMap map[string]interface{}
```

**矛盾点**：
- 该列语义是"部署ID**列表**"，`default:'[]'` 也是**数组**；
- 但 Go 类型是 map，只能反序列化 JSON **对象** `{}`；
- 一旦列中是数组，`json.Unmarshal` 必然报错。

**已实机复现**（抽取类型独立编译运行）：

```
输入 []        -> err=json: cannot unmarshal array into Go value of type main.JSONMap
输入 {}        -> err=<nil>
输入 [1,2]     -> err=json: cannot unmarshal array into Go value of type main.JSONMap
```

与线上报错逐字一致。

**加重因素**：`BeforeCreate` 钩子又把该字段初始化为 `JSONMap{}`（**对象**），与列默认值 `'[]'`（数组）自相矛盾，使"写入什么形态"取决于代码路径。

**影响面**：`DeploymentIDs` 在 Go 代码中**只被写入、从未被读取**，所以业务功能未受损，但**恢复流程被这个无关字段持续阻断**。

#### 改动

新增 `JSONArray` 类型（`models/workflow_schedule.go`）替换 `JSONMap`：

- 正常解析数组 `[]` / `[1,2]`；
- 对历史脏数据（`{}` / `null` / 空串）**宽松降级为空数组并打印告警**，不再抛错 —— 避免单行脏数据阻断整个恢复流程；
- `BeforeCreate` 改为初始化 `JSONArray{}`，与列默认值 `'[]'` 一致。

**修复后验证**（同样独立编译运行）：

```
输入 "[]"                  -> err=<nil> value=[]
输入 "[1,2]"               -> err=<nil> value=[1,2]
输入 "{}"                  -> err=<nil> value=[]   (告警降级)
输入 "null" / ""           -> err=<nil> value=[]
nil 驱动值                  -> err=<nil> value=[]
```

#### 影响

修复后 205 的上线恢复应能正常完成。**建议上线后确认日志中 `第NNNNN次尝试` 不再增长。**

> ⚠️ 注：本文档中"严格匹配"等结论不受此改动影响；这是独立发现的缺陷。
